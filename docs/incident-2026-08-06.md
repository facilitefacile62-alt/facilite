# Incident du 2026-08-06 — lecture publique de `public.profiles` (fait principal) + bucket `resumes` public (fait déclencheur)

Statut : **remédiation technique appliquée** sur les deux faits. Décision de
notification externe en attente (voir « Décisions restantes »).

## Résumé en une phrase

En cherchant l'origine d'un bucket de CV mal configuré, la vérification a
révélé un problème plus grave et plus large : une policy sur `public.profiles`
rendait la table entière — email, téléphone, date de naissance, statut
marital, permis de conduire, pour **tout compte, sans exception** —
lisible par n'importe qui, sans authentification, par une simple requête
REST ; les deux ont été fermés le jour même.

## Le fait principal : `public.profiles` ouverte à `anon`

### Ce qui était exploitable, vérifié en direct

Une policy nommée `"Profiles read access"` (`USING (true)`, rôle `public`),
combinée à un `GRANT SELECT` accordé à `anon`, autorisait une requête REST
anonyme (clé `anon`, publique par construction — embarquée dans tout bundle
client) à lire l'intégralité de la table. Vérifié par une requête réelle,
sans authentification :

```
GET /rest/v1/profiles?select=id,email,phone,birth_date,gender,marital_status
→ [{"id":"...","email":"...","phone":null,...}, ...]
```

Aucune ligne n'était filtrée : ni par `is_public`, ni par propriétaire, ni
par quoi que ce soit. Chaque compte de la plateforme était concerné, pas
seulement ceux ayant choisi la visibilité publique.

### Colonnes exactement exposées

Les **36 colonnes** de `public.profiles`, sans exception, étaient lisibles
par un appelant anonyme :

`id, email, full_name, avatar_url, created_at, updated_at, bio, headline,
location, experiences, cv_url, cover_url, cv_name, city, country,
profile_views, post_impressions, educations, pinned_details, phone,
marital_status, driver_license, website_url, birth_date, gender, slug,
languages, skills, interests, contact_email, is_public, show_contact,
education_level, recruiter_verified, badges, is_test_account,
cv_visible_recruteurs`

Parmi elles, directement sensibles : `email`, `phone`, `birth_date`,
`gender`, `marital_status`, `driver_license`, `cv_url`.

### Combien de comptes exactement

| | Nombre |
|---|---|
| Profils au total | 35 |
| dont comptes de test (`is_test_account = true`) | 24 |
| **dont comptes réels** | **11** |
| Comptes réels avec `email` renseigné | 7 |
| Comptes réels avec `phone` renseigné | 2 |
| Comptes réels avec `birth_date` renseigné | 1 |
| Comptes réels avec `marital_status` renseigné | 1 |
| Comptes réels avec `driver_license` renseigné | 1 |
| Comptes réels avec `cv_url` renseigné | 1 |

11 comptes réels au total sur la plateforme aujourd'hui — c'est un nombre
précis et vérifié, pas une estimation. Toutes les colonnes ci-dessus étaient
techniquement lisibles pour chacun des 11, qu'une valeur y soit renseignée ou
non (`full_name`, `city`, `bio`, `location` etc. comprises, même quand les
champs les plus sensibles étaient vides).

### Depuis quand — ❓ NON ÉTABLI, et c'est un fait en soi

Recherche exhaustive effectuée : **aucune trace, nulle part**.
- `grep` sur l'intégralité de `supabase/migrations/` : zéro occurrence de
  `"Profiles read access"`.
- `git log --all -S "Profiles read access"` sur tout l'historique du dépôt :
  les deux seuls commits trouvés sont ceux d'aujourd'hui (le mien, et un
  commit d'une session concurrente qui a involontairement embarqué un de mes
  fichiers non encore commité — vérifié, ce n'est pas une création
  indépendante de cette policy).

Contrairement au bucket `resumes` (où une chronologie de migrations permet de
borner une fenêtre), cette policy n'a **aucune trace écrite d'aucune sorte**
avant sa découverte aujourd'hui. Elle a donc pu exister depuis n'importe quel
point du projet, y compris depuis le tout début. Seuls les logs
d'infrastructure du Dashboard Supabase (hors de portée depuis cet
environnement) pourraient, si leur rétention le permet, donner une date.

## Le fait déclencheur : bucket `resumes` public

(Détail inchangé par rapport à la première version de ce document — conservé
ici pour la chronologie complète, mais ce n'est plus le fait le plus grave de
cet incident.)

- Créé public le 2026-07-27 (migration `20260727120000_cv_storage_bucket.sql`).
- Corrigé en privé le 2026-07-28 (migration `20260728180000_durcissement_securite_rls_storage.sql`,
  confirmée appliquée dans le registre `supabase migration list --linked`).
- Redevenu public entre le 2026-07-28 et le 2026-08-06 par un mécanisme non
  tracé dans aucune migration.
- 107 objets dans le bucket au moment de la découverte : 62 de test, **45
  répartis sur seulement 3 comptes réels** (`58b1e288-...`, `98f2b9a0-...`,
  `eda26422-...`), tous avec `cv_visible_recruteurs = false`.
- Hypothèse vérifiée et **écartée** : le backend FastAPI (`backend-api/`) a
  été suspecté de recréer le bucket en public à chaque démarrage. Recherche
  exhaustive (`create_bucket`, `createBucket`, `updateBucket`, toute mention
  de `storage`/`bucket`) dans tout le dépôt (Next.js, backend FastAPI,
  scripts, seed) : **aucune occurrence**, nulle part, en dehors du test
  d'invariant lui-même. Le backend se connecte via `SUPABASE_DATABASE_URL`
  (connexion Postgres directe via le pooler, rôle `postgres` — accès complet,
  équivalent superuser, aucune restriction technique), mais son code ne fait
  strictement que des `INSERT`/`SELECT` SQLAlchemy sur `establishments` et
  `job_offers`, jamais la moindre opération Storage. **Il n'est pas la cause**
  de ce fait précis — mais le risque que représente une chaîne de connexion à
  privilège complet dans `.env.local` reste noté séparément (voir
  « Constat annexe »).
- Origine réelle du repassage en public : ❓ NON ÉTABLIE, comme la policy
  `profiles` ci-dessus — un mécanisme hors du code de ce dépôt.

## Autres points trouvés en cherchant la classe complète (Partie 5), corrigés le même jour

- **`public.establishments`** (annuaire pharmacies/hôpitaux/hôtels, créé hors
  migration par `backend-api/database.py` via `Base.metadata.create_all()`) :
  `GRANT UPDATE, DELETE` accordé à `anon` **et** `authenticated`, sans aucune
  policy restrictive — n'importe quel visiteur pouvait vider ou modifier
  l'annuaire. Aucune donnée personnelle en jeu (uniquement des coordonnées
  d'entreprises), table actuellement vide (0 ligne), donc aucun impact réel
  constaté — mais un risque réel dès que le scraper la peuplera. GRANT retiré,
  policy de lecture remplacée par une version en lecture seule explicite,
  ajoutée à la liste blanche documentée de l'Invariant 7.
- **`is_app_admin(uuid)`** : fonction orpheline, aucune référence dans les
  migrations ni dans `src/`, vérifiait `profiles.role` — colonne du modèle
  pré-RBAC, remplacée depuis le 2026-08-02 par `public.user_roles`.
  Supprimée par migration.
- **`is_admin(check_user_id uuid)`** : légitimement utilisée (auto-vérification
  du rôle admin depuis une session authentifiée — `RoleNavLink.jsx`,
  `profil/page.js`, `admin/page.js`), mais `anon` avait `EXECUTE` dessus alors
  qu'aucun appelant anonyme légitime n'en a besoin — permettait de sonder le
  statut admin d'un uuid arbitraire sans authentification (reconnaissance à
  faible coût, aucune donnée directement exposée). `EXECUTE` retiré à `anon`,
  conservé pour `authenticated`.
- **Balayage complet des tables accordées à `anon`** (19 tables au total,
  liste dans le détail technique) : vérifié une par une avec une requête REST
  anonyme réelle. Seules deux renvoient des lignes : `job_offers` (offres
  publiques, comportement voulu) et `recruiter_profiles` (vitrine entreprise,
  déjà documentée et justifiée dans l'Invariant 7). Toutes les autres,
  `security_logs`, `messages`, `conversations`, `transactions`, `orders`,
  `candidatures`, `resumes`, `badge_requests`, `contact_messages`,
  `support_threads`, `user_roles`, `interviews`, `subscriptions`,
  `agent_assignments`, `assistant_messages`, `ai_usage_daily` — renvoient 0
  ligne à un appelant anonyme malgré le GRANT technique : le GRANT seul est
  inerte sans policy permissive, confirmé empiriquement table par table, pas
  supposé.

## Constat annexe (hors périmètre de correction de cet incident, à noter)

`SUPABASE_DATABASE_URL` (utilisée par `backend-api/`) est une connexion
Postgres directe avec un rôle à privilège complet (`postgres`, via le
pooler) — elle contourne entièrement la RLS par nature. Le code actuel ne
l'utilise que pour `establishments`/`job_offers`, mais la valeur elle-même,
si elle fuitait, donnerait un accès total à la base, pas limité à ces deux
tables. Hygiène des identifiants à revoir séparément — hors du périmètre de
cet incident.

## Faits NON établis (❓ NON VÉRIFIÉ)

- **Accès réels aux fichiers/lignes exposés**, pour les deux faits
  (`resumes` et `profiles`) : aucune table interrogeable en SQL depuis cet
  environnement ne journalise les requêtes REST/Storage. Filtre exact à
  appliquer vous-même dans le Dashboard, voir section suivante.
- **Indexation par un moteur de recherche** : aucun lien HTML public ne
  pointe vers un fichier `resumes/...` nulle part dans le code ; l'API REST
  `/rest/v1/profiles` n'est pas un objet crawlable au sens classique (pas de
  page HTML à indexer), mais reste interrogeable par script par quiconque en
  connaîtrait l'existence — non vérifiable depuis cet environnement.
- **Origine humaine ou automatisée** des trois changements hors migration de
  cet incident (bucket `resumes`, policy `profiles`, grant `get_profils_publics`)
  : non attribuable depuis le dépôt.

## Ce qu'il faut vérifier dans le Dashboard Supabase (à faire vous-même)

**Storage Logs** (Dashboard → Logs → Storage Logs, ou Logs Explorer si
disponible sur votre plan) :
- Filtre : `bucket_id = resumes` (ou recherche libre `resumes` si le champ
  structuré n'est pas disponible), méthode `GET`.
- Période : du **2026-07-27 00:00 UTC** (création du bucket, déjà public dès
  ce moment) au **2026-08-06** (jour de la correction) — toute la fenêtre
  possible, pas seulement depuis le 28.
- Ce qu'un accès légitime ressemble : des requêtes authentifiées émises par
  le serveur Next.js lui-même (User-Agent applicatif, IP d'infrastructure
  Vercel). Ce qui serait un accès non prévu : des GET directs sur des chemins
  `resumes/...` sans passer par une session applicative reconnue,
  particulièrement en dehors des heures d'usage normal du site, ou depuis des
  IP/User-Agents répétitifs suggérant un scan automatisé.

**API/PostgREST Logs** (Dashboard → Logs → API Logs / Postgres Logs) :
- Filtre : requêtes sur `/rest/v1/profiles`, méthode `GET`, **sans** en-tête
  d'autorisation utilisateur authentifié (c'est-à-dire portant uniquement la
  clé `anon`, pas un JWT de session) — c'est le signal d'un appel qui a
  emprunté exactement la faille ci-dessus plutôt que le chemin normal de
  l'application.
- Même période : 2026-07-27 à 2026-08-06 au minimum ; si votre plan conserve
  plus, remontez aussi loin que possible, l'origine réelle de la policy
  n'étant pas bornée.
